# Splatoon 3: initial native runtime findings

My separate [LAN/local-wireless audit](splatoon-3-local-network.md) records the title's actual network modes, imported ABI, native protocol-selector correction and outstanding physical peer tests. Those checks do not establish a local or online match.

On November 2, 2026, I began a private macOS bring-up of my own Splatoon 3 **11.3.0** dump (`0100C2500FC20000`, main build `28c4287aee36f7499da60f3e68b54c70`, SDK **20.5.22**). This note records a backend finding; it does not register a complete game profile or establish a playable export.

I compiled all 31,218 shader libraries with the existing translation chain `a7dbbce711c3`. A full pipeline-archive prebuild failed inside Apple's compiler. I therefore ran one private graphical diagnostic with the documented `--gpu none` and `DM_PSO_PREBUILD=0` options: the archive and eager prebuild were omitted, while normal Metal rendering and all shader libraries remained available. This diagnostic is not a correction or a stable release.

During initial startup I observed a real cube descriptor bound to a shader argument declared as a cube array. The [cube-to-cube-array binding correction](../reference/rendering.md#a-cube-view-read-as-a-one-element-cube-array) preserves the original texture storage and six face slices. I reproduced the missing view in an original synthetic Metal fixture and checked all six face orientations, mip selection, face offsets and channel swizzling on the GPU. The expanded fixture failed twice before the correction and passed all 47 checks afterward on an M5 Max with Metal API validation; the existing cube/volume placeholder fixture also passed all 63 checks.

The same startup attempt later aborted in the embedded gRPC poll-engine selector because its wakeup-descriptor availability check failed. The native EventFd hooks were unimplemented. I have now implemented [local event-counter descriptors](../reference/services.md#grpc-cannot-create-a-local-event-counter-wakeup-descriptor), including the offline availability probe and the observed creation flags, and checked the production HLE entries with original synthetic fixtures. On November 3, I repeated the isolated private diagnostic with that EventFd implementation and the cube-view correction. The original gRPC abort did not recur: the ordinary runtime log reached frame counter **11,400** without a fatal error or crash, and I closed the app normally with Command-Q. The window remained entirely black, so I have not verified a rendered scene. The separate conditional-render/invalid-clear warnings remain unexplained. I have not bypassed the game function or attributed the original abort to the texture warning.

### Small prerecorded-list capacity

In a later private diagnostic I enabled the runtime's existing conditional-render implementation through the game profile and checked a correctly rendered character-selection scene and tutorial. I preserved the shader libraries and translation chain. The runtime subsequently exhausted the 1 GB host command-memory cap during continued startup; my diagnostic logged 4,096 occupied 256 KB segments, with no unknown-origin segments, and mostly 512-byte grants in the sampled small-list allocations. This result does not establish stable gameplay or online play.

I reduced [small prerecorded-list overflow capacity](../reference/nvn-objects.md#host-lent-command-memory-segments) to a 4 KB bucket while retaining the last real grant's capacity, large-record support, the 1 GB cap and the existing lifetime rules. My original fixture keeps 2,048 handles live with at most 8 MB of additional host capacity, rather than roughly 512 MB, and replays them after command-buffer finalization. All 219 `t_nvn` checks pass with Metal API validation, both normally and under ASan/UBSan; the changed recording code also compiles for arm64 iOS with warnings treated as errors.

I then repeated the private Mac run using a copy of my save and the same shader libraries. I passed the tutorial/train transition and reached the plaza; the ordinary runtime frame counter exceeded **40,500** without the former fatal error. Host segment capacity remained approximately **61 MB** for more than **12,000 further frames** after its last allocation at frame 27,903. This qualifies the formerly failing transition, not long-session stability or every scene: I still observed serious plaza color/texture corruption and a return from the online lobby with NPLN error **2321-4992**. The process stayed alive during that connection failure. I have not attributed the visual or network symptoms to command-memory capacity.

I have not verified LAN/LDN discovery, Nextendo authentication or a completed match in this native build. The backend fixture does not establish those outcomes. Game files, generated shader libraries, firmware resources, keys and saves remain private.

In the next private diagnostic, account preflight and availability succeeded, while the lobby returned `2321-4992` with only single-descriptor wakeup Polls and no traced socket creation. I then traced [the C resolver's independent plain-struct ABI](../reference/services.md#the-c-resolver-fails-when-an-sdk-exports-both-c-layouts): this SDK exports both C++ layouts, but its C wrapper forwards to plain `struct addrinfo`. My host incorrectly rejected that combination before DNS resolution. I reproduced the rejection in the actual HLE fixture and corrected the C entry without changing either C++ entry, service policy or graphics. Error-only resolver metadata now covers failures before Socket. The following private native attempt opened TCP sockets and reached Connect `-1`/`EINPROGRESS(115)`, with no resolver error, but the lobby still returned `2321-4992`.

I then traced [the separate C errno cell](../reference/services.md#a-c-socket-caller-reads-a-different-errno-after-nonblocking-connect): the gRPC caller reads `__errno_location()` directly after Connect, while my native replacement only updated its own socket cell. I corrected the shared pointer-getter ABI without any SDK TLS offset and reproduced the old separation in a synthetic HLE control. Real loopback TCP, the caller's EINPROGRESS branch, writable Poll, SO_ERROR, offline errors and independent thread cells are covered. I have not yet qualified another native online attempt with this correction; it does not establish a successful NPLN session or match.

I also checked the public BCAT imports against SDK 20. Its directory-scoped synchronization overload opens its own IPC service instead of delegating to the older whole-cache overload. I added [a native scoped observer](../reference/services.md#a-newer-bcat-directory-scoped-request-enters-unavailable-sdk-ipc), with exact directory-name validation and downloaded bytes from the selected directory in one real immutable refresh snapshot. I keep progress state host-owned and do not initialize or pass a guessed private SDK object to its original Attach routine. The S3 recipe separately validates the provider's region-specific encrypted schedule envelopes and checks for updates on each online launch. The synthetic downloader, guest-call and lifecycle checks do not establish acceptance by the real game's schedule decoder.

I separately imported the upstream [conditional-report capacity correction](../reference/rendering.md#conditional-reports-dropped-after-fixed-tracking-limits), attributed to seedds. My synthetic fixture reproduces the old tracking limits without using game data. The ordinary Splatoon 3 diagnostic did not count report-table saturation, so I have not established that mechanism as its plaza-color root cause or verified the imported correction in this game yet.
